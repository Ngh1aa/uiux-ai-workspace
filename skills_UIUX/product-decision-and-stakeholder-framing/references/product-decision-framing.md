# Product Decision & Stakeholder Framing — Pinned Synthesis

Source reviewed: `mindtheproduct/skills@3fb3d46092c4149d1653fc317aed77d63f2a98ca` → `make-the-call` (MIT).

This reference adapts the three-stage reasoning practice to `skills_UIUX` project truth, evidence labels, autonomous project phases and explicit decision ownership. It is not a verbatim copy.

## Stage 1 — Boil the ask down

Goal: separate requested solutions from the problems/outcomes beneath them.

For each voice/request:

```text
ask → who/what is affected → underlying problem → observable consequence → evidence pointer
```

Useful probes when interactive:
- What is the customer/user actually trying to accomplish by asking for this?
- What risk is engineering/operations/brand/sales trying to reduce?
- If we could not implement the requested solution, what problem would still remain?

Exit when every material ask has a problem statement that does not merely repeat the requested feature/change.

## Stage 2 — Stress test

Run these three questions for each candidate problem:

1. **Evidence — how do we know?** Direct behavior/research, analytics/support/sales evidence, stakeholder assertion, or assumption?
2. **Blind spots — what else could it be?** Name a plausible alternate explanation or contradictory signal.
3. **Impact — would solving it matter?** What user/business/system outcome changes, and how would we observe it?

Kill weak problems explicitly rather than carrying them forward out of politeness.

## Stage 3 — Pick what matters

Use three lenses without pretending they are universal weights:

- **Leverage:** which problem is upstream or unlocks others?
- **Cost of being wrong / reversibility:** which wrong call is hardest to recover from?
- **Strategic ground:** which problem most affects the current business/user outcome, trust obligation or product direction?

The authorized human/project owner makes the final call. If ranking now requires Reach/Impact/Confidence/Effort or scope shaping, hand off to `product-strategy-and-prioritization`.

## Autonomous-mode adaptation

When operating inside a project phase instead of a live coaching conversation:
- read project truth/evidence first;
- synthesize documented asks and stakeholder voices;
- mark missing perspectives UNKNOWN;
- do not manufacture the minimum number of dialogue turns used by the original interactive practice;
- record material conflicts in Decision Log.
